## 1. Побудова та логіка Dockerfile

Для забезпечення ізоляції застосунку було розроблено Dockerfile, що базується на стратегії багатоетапної збірки. На першому етапі, який виступає в ролі середовища збірки, використовується базовий образ Python 3.11-slim. Тут виконується підготовка інструментарію, що включає встановлення системних залежностей через пакетний менеджер apt та інсталяцію Poetry. Процес конфігурується таким чином, щоб віртуальне середовище створювалося безпосередньо в робочій директорії проєкту, що дозволяє чітко відокремити встановлені бібліотеки від системних пакетів. Після копіювання файлів конфігурації виконується встановлення лише виробничих залежностей, що гарантує відсутність зайвого інструментарію для розробки у фінальному образі.

Другий етап орієнтований на створення максимально легкого та безпечного середовища виконання. Замість копіювання всього інструментарію з попереднього етапу, сюди переноситься лише готове віртуальне середовище та вихідний код застосунку. Для підвищення безпеки всередині контейнера створюється окремий непривілейований користувач vfsuser, від імені якого запускаються всі процеси. Це мінімізує ризики у разі потенційного зламу системи. Фінальне налаштування включає оновлення змінних середовища для коректного виклику Python та визначення точки входу, яка автоматично запускає основний скрипт системи при старті контейнера, забезпечуючи готовність до інтерактивної роботи користувача.

## 2. Структура пайплайну безперервної інтеграції (CI)

Процес безперервної інтеграції реалізовано через файл конфігурації GitHub Actions, який описує послідовність кроків для перевірки стабільності коду при кожному оновленні репозиторію. Робочий процес розгортається на віртуальній інфраструктурі Ubuntu та розпочинається з ініціалізації середовища Python. Ключовим елементом архітектури пайплайну є гнучка система кешування: вона зберігає стан встановлених пакетів Poetry та віртуального середовища, спираючись на унікальну хеш-суму конфігураційного файлу проєкту. Це дозволяє значно скоротити час виконання повторних перевірок, оскільки повторне завантаження бібліотек відбувається лише при реальній зміні списку залежностей.

Після підготовки середовища виконується комплексний аналіз коду, що поєднує статичну перевірку та динамічне тестування. Спочатку запускається лінтер Ruff, який аналізує синтаксичну коректність та відповідність стилістичним нормам, блокуючи подальше виконання у разі виявлення помилок. Наступним етапом є запуск юніт-тестів за допомогою pytest, що супроводжується аналізом покриття коду. Результати тестування оформлюються у вигляді детального HTML-звіту, який завантажується як артефакт GitHub для подальшого аудиту. Весь цикл замикається фінальною перевіркою статусу, яка інтегрує результати всіх кроків і надає остаточне підтвердження цілісності збірки, що є критичним для підтримки високої якості програмного продукту.

## 3. Структура пайплайну безперервного розгортання (CD)

Пайплайн безперервного розгортання спроєктований як багаторівнева система автоматизації, що активується виключно при публікації нових версійних тегів. Перша фаза присвячена створенню стандартних дистрибутивів Python. Використовуючи потужності Poetry, система збирає вихідні архіви та wheel-пакети, які є універсальними форматами для встановлення бібліотек. Ці файли тимчасово зберігаються всередині пайплайну для використання на наступних етапах. Паралельно з цим запускається процес формування Docker-образу, де за допомогою Docker Buildx виконується збірка контейнера, його авторизація в реєстрі GitHub Container Registry та автоматичне тегування версією, взятою безпосередньо з назви Git-тегу.

Фінальна стадія пайплайну відповідає за публічне представлення релізу та координацію всіх створених артефактів. Після успішної збірки пакетів та образів система ініціює створення офіційного релізу на GitHub. На цьому етапі виконується автоматична генерація документації: спеціальний скрипт формує опис релізу, додаючи туди інструкції з експлуатації та посилання на нові версії образів. Завершальним акордом є публікація Release Notes та прикріплення зібраних архівних файлів до сторінки релізу. Таким чином, весь цикл від написання коду до появи готового продукту в різних форматах (Docker-образ та Python-пакет) стає повністю автоматизованим, що виключає помилки ручного керування версіями.
