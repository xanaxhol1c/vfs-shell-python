## 1. Контекст та Проблема
Поточна архітектура віртуальної файлової системи базується на класі File, який зберігає дані у відкритому вигляді. Виникла потреба впровадити механізми прозорого шифрування та стиснення даних без зміни логіки існуючих команд.

**Основні складові проблеми:**
* **Принцип відкритості/закритості**: Команди на кшталт **cat** та **write** не повинні містити логіку перевірки типу файлу. Будь-яке пряме впровадження умовних операторів для перевірки, чи є файл зашифрованим, порушує стабільність ядра системи та ускладнює подальше розширення.
* **Багатошаровість обробки:** Система повинна підтримувати комбінування функцій. Наприклад, файл може бути спочатку стиснутим для економії місця, а потім зашифрованим для безпеки. Реалізація цього через звичайне успадкування призвела б до створення надмірної кількості класів.
* **Зовнішнє керування:** Необхідно відокремити бізнес-логіку від налаштувань. Система має автоматично визначати необхідність обробки даних на основі шляху до файлу, використовуючи зовнішній конфігураційний файл, що дозволяє змінювати поведінку системи без її перекомпіляції.

## 2. Рішення
Для вирішення проблеми обрано патерн проектування **Decorator** у поєднанні з **Factory** та допоміжними механізмами конфігурування.

### Деталі реалізації:
1. **Створення абстракції:** Впроваджено інтерфейс IVirtualFile, який визначає обов'язкові методи read та write. Це дозволяє системі взаємодіяти з будь-яким об'єктом файлу однаково, незалежно від того, чи є він базовим файлом, чи "обгорнутим" декоратором.
2. **Патерн Декоратор:** Реалізовано базовий клас FileDecorator та його конкретні розширення:
    - EncryptedFileDecorator використовує кодування Base64 для імітації шифрування. Він перехоплює потік даних: при записі — кодує текст, при читанні — декодує його назад.
    - CompressedFileDecorator: виконує стиснення даних шляхом нормалізації пробілів, що зменшує фізичний розмір контенту перед його збереженням.
3. **Керування через конфігурацію:** Створено клас ConfigManager, який під час старту програми зчитує файл vfs_config.json. Це дозволяє задавати правила (наприклад, "автоматично шифрувати все в папці /secret").
4. **Прозоре створення через Фабрику:** Клас FileFactory інкапсулює логіку збірки об'єктів. Коли команда touch ініціює створення файлу, фабрика перевіряє правила в менеджері конфігурацій і автоматично "нашаровує" потрібні декоратори на базовий об'єкт файлу. Таким чином, команда отримує вже готовий до роботи об'єкт, не знаючи про його внутрішню структуру.


## 3. Наслідки
Впроваджені зміни дозволили досягти наступних результатів:

**Позитивні наслідки:**
* **Чистота коду та дотримання принципів SOLID:** Основне ядро системи (команди, двигун виконання) залишилося незмінним. Команда cat просто викликає метод читання, а декоратори самі розшифровують дані "на льоту". Це забезпечує повну прозорість функціонала для кінцевого користувача.
* **Гнучкість та масштабованість:** Додавання нових способів обробки даних (наприклад, перевірка цілісності або логування) тепер вимагає лише створення нового декоратора та оновлення фабрики, що не впливає на працездатність існуючих модулів.
* **Успішне регресійне тестування**: Завдяки збереженню існуючих інтерфейсів, усі тести з попередніх етапів розробки проходять успішно без внесення змін у їхній код.

**Ризики та особливості:**
* **Облік дискового простору:** Використання декораторів впливає на метод get_size. Оскільки стиснення зменшує обсяг даних, а шифрування може його збільшити, система квот тепер враховує саме модифікований розмір файлу. Це забезпечує точне відображення стану віртуального диска, але потребує уваги при тестуванні лімітів пам'яті.
* **Складність відлагодження:** Через використання ланцюжка декораторів, прямий перегляд вмісту об'єкта в пам'яті може бути ускладнений, оскільки дані проходять через декілька етапів трансформації.
