# ADR-0001: Прозоре шифрування та стиснення файлів (Transparent File Processing)

**Дата:** 2026-04-02
**Статус:** Ухвалено (Accepted)
**Контекст:** Лабораторна робота №4 (Симулятор VFS Shell)

## 1. Контекст та Проблема
Поточна реалізація віртуальної файлової системи (VFS) зберігає дані у класі `File` у вигляді звичайного тексту (через поле `self.content`). Згідно з новими вимогами, необхідно додати функціонал прозорого шифрування та стиснення файлів. 

**Головні виклики:**
* **OCP (Open/Closed Principle):** Існуючі команди (наприклад, `cat` або `write`) та ядро (`ExecutionEngine`) не повинні нічого знати про те, що файл зашифрований чи стиснутий. Ми не можемо додавати численні `if is_encrypted:` всередині `models.py` або `commands.py`.
* **Динамічність:** Файл може бути одночасно і зашифрованим, і стиснутим (нашарування).
* **Конфігурованість:** Правила застосування цих модифікацій повинні завантажуватися із зовнішнього JSON/YAML файлу під час старту програми та залежати від шляху (наприклад, папка `/secret`).

## 2. Рішення (Decision)
Для вирішення проблеми обрано патерн проектування **Decorator (Декоратор)** у поєднанні з **Simple Factory (Фабрика)** та **Configuration Management**.

### Чому саме Decorator?
Декоратор дозволяє динамічно додавати нову поведінку об'єктам без зміни їхнього коду. Замість створення підкласів `EncryptedFile`, `CompressedFile`, `EncryptedCompressedFile` (що призведе до вибуху кількості класів), ми створимо обгортки (wrappers), які реалізують єдиний інтерфейс.

Альтернативою міг би бути патерн *Strategy*, але Стратегія краще підходить для вибору *одного* алгоритму поведінки, тоді як нам потрібно *нашаровувати* їх (ланцюжок: Стиснення -> Шифрування -> Запис у пам'ять).

### Архітектурний план:
1. **Інтерфейс `IVirtualFile`**: Виділяється загальний абстрактний інтерфейс для роботи з даними файлу (`read()`, `write(data)`).
2. **Декоратори**: Створюються класи `EncryptedFileDecorator` (алгоритм ROT13/Base64) та `CompressedFileDecorator` (видалення зайвих пробілів).
3. **Менеджер Конфігурацій (`ConfigManager`)**: Новий модуль, який парсить JSON і при створенні файлу вказує фабриці, в які декоратори його потрібно обгорнути.

## 3. Наслідки (Consequences)
**Позитивні:**
* **Строге дотримання OCP:** Базові класи `File` та команди з модуля `commands.py` залишаються практично незмінними (лише перехід від прямого доступу до `self.content` на виклик `read()/write()`).
* **Відсутність регресії:** Старі юніт-тести не зламаються, оскільки базовий клас `File` продовжує працювати як і раніше.
* **Гнучкість:** Легко додати новий декоратор (наприклад, `HexDumpDecorator`) без зміни існуючої архітектури.

**Можливі ризики (Trade-offs):**
* Підрахунок розміру (`get_size()`): Декоратори повинні коректно перевизначати метод `get_size()`, щоб команда `ls` показувала розмір саме модифікованих (стиснутих/зашифрованих) даних, а не оригінального тексту.

## 4. Технічна структура майбутніх змін (Implementation Plan)

### Крок 1: Модифікація `models.py` (Підготовка інтерфейсу)
Зараз `File` використовує прямий доступ до `self.content`. Необхідно інкапсулювати це.

```python
class IVirtualFile(INode):
    @abstractmethod
    def read(self) -> str: pass
    
    @abstractmethod
    def write(self, data: str) -> None: pass

# Зміна у класі File:
class File(IVirtualFile):
    # ... init ...
    def read(self) -> str:
        return self.content
        
    def write(self, data: str) -> None:
        self.content = data
