# ADR-0001: Прозоре шифрування та стиснення файлів

**Дата:** 2026-04-02
**Контекст:** Лабораторна робота №4 (VFS Shell)

## 1. Контекст та Проблема
Поточна реалізація віртуальної файлової системи (VFS) зберігає дані у класі `File` у вигляді звичайного тексту (через поле `self.content`). Згідно з новими вимогами, необхідно додати функціонал прозорого шифрування та стиснення файлів. 

**Головні задачі:**
* **Open/Closed Principle:** Існуючі команди (наприклад, `cat` або `write`) та ядро (`ExecutionEngine`) не повинні нічого знати про те, що файл зашифрований чи стиснутий. Ми не можемо додавати численні `if is_encrypted:` всередині `models.py` або `commands.py`.
* **Динамічність:** Файл може бути одночасно і зашифрованим, і стиснутим (нашарування).
* **Конфігурованість:** Правила застосування цих модифікацій повинні завантажуватися із зовнішнього JSON/YAML файлу під час старту програми та залежати від шляху (наприклад, папка `/secret`).

## 2. Рішення
Для вирішення проблеми обрано патерн проектування **Decorator** у поєднанні з **Simple Factory** та **Configuration Management**.

### Чому саме Decorator?
Декоратор дозволяє динамічно додавати нову поведінку об'єктам без зміни їхнього коду. Замість створення підкласів `EncryptedFile`, `CompressedFile`, `EncryptedCompressedFile` (що призведе до занадто великої кількості класів), ми створимо обгортки, які реалізують єдиний інтерфейс.


### Архітектурний план:
1. **Інтерфейс `IVirtualFile`**: Виділяється загальний абстрактний інтерфейс для роботи з даними файлу (`read()`, `write(data)`).
2. **Декоратори**: Створюються класи `EncryptedFileDecorator` (алгоритм ROT13/Base64) та `CompressedFileDecorator` (видалення зайвих пробілів).
3. **Менеджер Конфігурацій (`ConfigManager`)**: Новий модуль, який парсить JSON і при створенні файлу вказує фабриці, в які декоратори його потрібно обгорнути.

## 3. Наслідки
**Позитивні:**
* **Строге дотримання OCP:** Базові класи `File` та команди з модуля `commands.py` залишаються практично незмінними (лише перехід від прямого доступу до `self.content` на виклик `read()/write()`).
* **Відсутність регресії:** Старі юніт-тести не зламаються, оскільки базовий клас `File` продовжує працювати як і раніше.
* **Гнучкість:** Легко додати новий декоратор без зміни існуючої архітектури.

**Можливі ризики (Trade-offs):**
* Підрахунок розміру (`get_size()`): Декоратори повинні коректно перевизначати метод `get_size()`, щоб команда `ls` показувала розмір саме модифікованих (стиснутих/зашифрованих) даних, а не оригінального тексту.
